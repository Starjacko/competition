# 接口实现与公司服务器验收说明

> 最后更新：2026-09-17
>
> 本文说明当前程序如何对接比赛判题器，以及怎样一步步证明“能提交、能启动、能被调用、能连续运行”。

## 1. 公司接口给出的硬性要求

根据 [接口文档](接口文档.md) 和 [任务书](任务书.md)：

- 每局双方程序会同时启动；
- 程序必须通过 HTTP Server 监听端口；
- 启动示例是 `bash run.sh port`；
- IP 应监听 `0.0.0.0`；
- 判题器向程序发送当前回合的 JSON；
- 程序返回 JSON 格式的 `roleCommandMap`；
- 每个角色每回合最多一条指令；
- 建立连接超过10秒，或连接后5秒内没有响应，会被判定为超时；
- 指令字段缺失、动作码不认识或响应格式错误，会产生异常；
- 单队异常达到5次后，后续回合不再调度该队伍代码；
- `executeCmd` 最长执行15秒，且只在任务期间可用。

## 2. 当前程序的实际启动方式

公司已确认服务器运行命令为 `python main3.py <port>`。当前仓库有 [main3.py](../Demo/CoreGeek/main3.py)，它要求一个端口参数：

```bash
cd Demo/CoreGeek
python main3.py 18080
```

程序会：

1. 检查是否只有一个端口参数；
2. 切换到 `Demo/CoreGeek`；
3. 把 `src` 加到 Python 模块路径；
4. 导入 `agent.server`；
5. 监听 `0.0.0.0:18080`。

因此，服务器提交包的工作目录必须是 `Demo/CoreGeek`，并执行：

```bash
python main3.py <port>
```

不需要额外依赖 `run.sh`。如果服务器从仓库根目录启动，则启动器必须先进入 `Demo/CoreGeek`，否则找不到 `main3.py`。

## 3. HTTP 请求和响应链路

```text
判题器
  │ POST JSON
  │ Content-Length + UTF-8
  ▼
server.Handler.do_POST
  │ json.loads
  ▼
brain.decide
  │ Turn.load + 白天/黑夜策略
  ▼
{"roleCommandMap": {"角色ID": {"action": "..."}}}
```

当前 [server.py](../Demo/CoreGeek/src/agent/server.py) 没有检查 URL 路径，也没有专门处理 GET；公司判题器如果只使用 POST 且不要求固定路径，这通常可以工作，但必须用公司提供的真实调用方式确认。

## 4. 当前响应实现覆盖范围

当前程序能够生成：

- `move`：包含一个 `targetPos`；
- `collect`：包含一个矿区 `targetPos`；
- `build`：包含 `name` 和一个 `targetPos`；
- `attack`：包含 `controllerId` 和目标 `targetPos`；加特林/火箭会按等级补足目标数量。

当前程序已经能生成：

- `sell` 的 `name`、`num`，并参考 `vendorShopList` 选择价格最高的矿石；
- `buy` 的 `name`、`num`，当前用于维护用品、升级券和基础攻击道具；
- `acceptTask`；
- `use` 的 `name` 和可选目标，当前用于药品、修墙包、升级券、炸弹和眩晕法宝。

当前策略仍没有主动生成：

- `remove`；
- `submitAnswer` 的 `taskAnswer`；
- `summonTreasure` 的 `item`；
- `drop` 的 `name`。

另外，接口文档允许加特林和火箭一次提交多个攻击目标，当前代码已按武器等级提交目标数量；当可攻击机器人不足时，会重复最优目标坐标。这个规则仍需公司判题器确认是否接受重复坐标。

## 5. 提交前的本地检查

本地检查不能代替真实对局，但可以提前发现“程序根本启动不了”或“JSON 格式坏了”。建议至少完成以下检查。

### 5.1 Python 版本和依赖

当前 [pyproject.toml](../Demo/CoreGeek/pyproject.toml) 要求 Python `>=3.11`，且没有第三方运行依赖。服务器上应确认：

```bash
python --version
```

输出版本必须不低于3.11。然后在项目目录执行：

```bash
python -m py_compile main3.py src/agent/*.py
```

如果公司要求安装项目包，再执行：

```bash
python -m pip install .
```

但当前入口脚本自己配置了 `src` 路径，是否需要安装包要以公司运行方式为准。

### 5.2 启动和端口检查

启动：

```bash
python main3.py 18080
```

另开终端确认端口监听：

```bash
curl -i -X POST http://127.0.0.1:18080/ \
  -H 'Content-Type: application/json' \
  --data-binary @../../docs/request.txt
```

实际执行前要确认 `request.txt` 是纯 JSON 文件；样例文件若含有说明文字或格式问题，需要先使用公司给出的真实请求样例。返回必须满足：

- HTTP 状态是成功状态；
- 响应是合法 JSON；
- 顶层有 `roleCommandMap`；
- 每个角色 ID 对应一个对象；
- 每个对象至少有合法的 `action`；
- 动作需要的 `targetPos`、`controllerId`、`name`、`num`、`taskAnswer`、`item` 等字段齐全；
- 同一个角色 ID 不重复提交多条指令。

### 5.3 用样例检查业务合法性

至少准备五类请求样例：

1. 白天、有石矿、金币不足；
2. 白天、有金币、可以建造；
3. 黑夜、机器人在武器射程内；
4. 黑夜、机器人不在射程内，需要移动操控者。
5. 白天、小贩价格变化，检查是否优先卖高价矿石；黑夜、机器人密集时检查炸弹/眩晕法宝和多目标攻击。

每个样例都要检查动作是否符合任务书，而不只是检查 JSON 能否解析。

## 6. 公司服务器验收顺序

### 第一步：确认提交规则

向公司赛事负责人确认并记录以下信息：

- 提交的是整个 Git 仓库、压缩包，还是指定目录；
- 默认工作目录是什么；
- 启动命令已经确认是 `python main3.py <port>`；
- Python 版本是否满足 `>=3.11`；
- 端口号如何传给程序；
- 判题器请求的 URL 路径、HTTP 方法和请求头；
- 单回合响应时间限制；
- 日志在哪里查看；
- 如何获取比赛编号、得分、胜负和异常次数。

这些答案没有拿到前，不能声称已经完成服务器适配。

### 第二步：做服务器启动验收

用一个测试端口启动，记录完整命令和输出：

```bash
python main3.py <公司分配的端口>
```

验收标准：

- 进程没有立即退出；
- 日志出现 `listening on 0.0.0.0:<port>`；
- 服务监听的是 `0.0.0.0`，不是只监听 `127.0.0.1`；
- 判题器所在环境能够访问这个端口；
- 端口冲突、权限和工作目录都没有问题。

### 第三步：做单回合接口验收

用公司提供的真实请求或判题器测试模式发送一回合请求。记录：

- 请求时间；
- HTTP 状态码；
- 响应耗时；
- 原始响应；
- 响应 JSON 解析结果；
- 判题器是否报告字段错误。

验收标准是：在5秒限制内返回合法 JSON，动作字段符合当前回合和角色规则。

### 第四步：做连续回合验收

不能只测一回合，因为程序每回合依赖新状态。至少观察白天到黑夜的切换，并确认：

- 每回合都能及时响应；
- 没有因某个坏请求导致进程退出；
- 角色动作失败后不会无限重复同一个非法动作；
- 火箭冷却、角色死亡、矿区消失等状态变化不会让程序崩溃；
- 日志没有持续异常。

### 第五步：做真实对局验收

和另一名员工的程序进行真实对局，并记录：

- 代码 commit ID；
- 比赛/服务器编号；
- 对手匿名标识；
- 是否成功启动；
- 运行回合数；
- 胜负和得分；
- 异常次数、超时次数和错误码；
- 服务器日志位置；
- 下一轮要改什么。

只有这一步完成，才能判断策略是否真的能应对对手。单回合接口通过不等于比赛胜利。

## 7. 发现问题时怎么判断

| 现象 | 可能原因 | 应检查 |
|---|---|---|
| 进程一启动就退出 | 没传端口、Python 版本不对、目录不对 | 启动命令、工作目录、Python 版本 |
| 判题器连不上 | 监听地址或端口错误 | `0.0.0.0`、端口传递、防火墙 |
| 5秒内没响应 | 决策卡住、路径搜索太慢、进程异常 | 服务器日志、请求耗时 |
| 响应格式错误 | 字段名、类型或 JSON 结构不对 | `roleCommandMap` 和动作字段 |
| 指令错误次数增加 | 目标不相邻、白天攻击、背包/金币不足、冷却未结束 | `lastRoundRoleActionResults`、错误信息和规则 |
| 程序一直返回空动作 | `Turn.load` 或 `brain.py` 抛异常 | 服务器日志；当前 `server.py` 会把异常隐藏成空响应 |
| 运行一段时间后策略变差 | 没有保存任务、资源和失败反馈 | 请求字段建模、决策状态和真实对局日志 |

## 8. 最终“可以提交并正常执行”的证据包

建议每次提交服务器前保存一份记录，至少包括：

- Git commit ID；
- 提交包文件名或仓库版本；
- 公司要求的启动命令；
- Python 版本和依赖安装结果；
- 启动日志；
- 单回合请求/响应摘要；
- 连续回合运行结果；
- 异常和超时计数；
- 真实对局结果。

判断标准可以分成三层：

| 层级 | 能证明什么 | 还不能证明什么 |
|---|---|---|
| 本地检查通过 | 代码能解析、能启动、样例 JSON 基本正确 | 公司环境和真实对手一定正常 |
| 服务器运行通过 | 判题器能启动并调用程序 | 策略能赢、长时间不出错 |
| 真实对局通过 | 在实际对手和规则下完成比赛 | 下一场一定还能赢，仍需持续记录和改进 |
