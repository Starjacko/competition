# 《未来战争》Demo 策略设计与完善计划

## 1. 文档目的

本文档用于指导 `Demo/CoreGeek/` 的后续完善工作。

约定如下：

- `Demo/CoreGeek/` 是唯一正式实现目录。
- `Demo/CoreGeek.tar.gz` 仅作为历史归档，不再作为开发目录。
- 当前文档同时作为实现依据和验收清单；正式实现统一放在 `Demo/CoreGeek/`。
- 已实现逻辑必须以任务书和接口文档为准，复杂策略配有简洁注释。

## 2. 项目目标

将当前 Demo 从“能接收请求并返回简单动作”的样例，逐步完善为可以参加完整对局的策略 Agent，覆盖：

1. 稳定的 HTTP 服务和 JSON 响应。
2. 完整的地图、单位、机器人和敌方信息解析。
3. 正确的昼夜识别和回合调度。
4. 白天采矿、交易、建造、升级和任务。
5. 夜间角色操控武器、防守基地和处理机器人。
6. 世界新闻、长上下文任务和宝藏任务。
7. 动作合法性检查、冲突规避和异常降级。
8. 可重复的本地模拟测试和日志分析。

当前已经具备：

- 还需要补充本地测试夹具和长时间模拟。

## 4. 总体架构

正式实现建议保持单进程 HTTP Agent，但在代码内部分层：

```text
main3.py
└── server.py                 HTTP 接入和响应兜底
    └── brain.py              回合策略编排
        ├── protocol.py       请求模型和动作构造
        ├── grid.py           地图、障碍和寻路
        ├── memory.py         跨回合记忆
        ├── validator.py      动作合法性检查
        ├── economy.py        采集、卖矿、购买和升级
        ├── tasks.py          任务、新闻和宝藏
        └── combat.py         夜间防守和武器目标
```

初期可以继续集中在现有文件中实现；当单个文件职责明显过多时，再拆分模块。
拆分时必须保持 `main3.py` 的启动方式不变：

```bash
python main3.py <port>
```

## 5. 回合总流程

每个回合严格按照以下顺序处理：

```text
1. 接收并解析 Request。
2. 构造本回合不可变状态 TurnState。
3. 更新跨回合记忆。
4. 识别第几天、白天/黑夜和昼夜边界。
5. 清理死亡角色、失效目标和已完成任务。
6. 评估基地、武器和围墙的安全状态。
7. 生成角色目标。
8. 依据当前阶段生成候选动作。
9. 做动作合法性检查。
10. 处理角色之间的目标冲突。
11. 保证每个角色最多保留一条动作。
12. 序列化为合法 Response。
```

### 5.1 阶段判断

任务书规定白天 70 回合、黑夜 60 回合，每天 130 回合。

```text
day_index = (roundNo - 1) // 130 + 1
phase_round = (roundNo - 1) % 130 + 1
白天：phase_round <= 70
黑夜：phase_round > 70
```

实现时应以 `roundNo` 为准，不依赖外部传入的阶段字符串。

### 5.2 每日边界处理

每天第一个白天回合：

- 清理上一晚残余机器人带来的临时目标。
- 读取并保存新的官方消息和民间传闻。
- 重置当日 LLM 调用计数。
- 重新评估卖矿价格。
- 检查角色是否可以复活。
- 重新安排工人、开拓者和武器控制关系。

每天第一个黑夜回合：

- 识别机器人波次和机器人类型。
- 计算基地方向上的主要威胁。
- 确定每座武器的控制角色。
- 提前将角色移动到武器周围一格内。

## 6. 状态模型设计

### 6.1 地图状态

地图状态至少需要提供：

```text
width, height
zones
our_units
enemy_units
robots
```

统一提供以下查询：

```text
inside(pos)
distance(a, b)
adjacent(a, b)
walkable(pos, role)
blocked_cells(role)
neighbors(pos)
path(start, goal)
```

距离必须使用切比雪夫距离：

```text
max(abs(x1 - x2), abs(y1 - y2))
```

### 6.2 单位状态

统一解析以下字段：

```text
id
pos
roleType
health
attackPower
attackRange
backPackCapability
backpack
level
cooldown
```

基地必须按 2×2 占地处理。敌方基地和围墙虽然受到视野规则影响较小，但仍应进入障碍和威胁计算。

### 6.3 跨回合记忆

建议维护一个轻量的进程内记忆对象：

```text
day_index
news_history
active_task
task_start_round
best_task_answer
task_output_history
treasure_clues
role_assignments
target_assignments
last_commands
daily_llm_calls
daily_summon_order_uses
```

如果服务重启，记忆可以丢失，但不能因此导致接口异常；所有字段都必须有默认值。

## 7. 角色分工策略

### 7.1 默认分工

```text
worker1：石头、围墙、近基地建设
worker2：铁矿/铜矿、卖矿、武器建设和升级辅助
pioneer：任务、宝藏、夜间武器控制补位
```

角色 ID 不能写死为唯一方案，应按 `roleType` 和实际存活状态识别。
接口中的固定 ID 可作为优先排序，但不能替代状态解析。

### 7.2 动态重分配

出现以下情况时重新分配：

- 工人死亡。
- 开拓者死亡。
- 某座武器没有控制角色。
- 基地附近出现高威胁机器人。
- 一名工人的目标长期无法到达。

动态分配原则：

```text
紧急防守 > 任务提交 > 武器控制 > 修墙 > 建造 > 采矿 > 卖矿
```

## 8. 白天策略

### 8.1 白天总优先级

```text
基地保命
> 复活和治疗
> 修复关键围墙
> 建造缺失武器
> 建造防线
> 完成/提交任务
> 购买必要升级
> 采集石头
> 采集高价矿石
> 卖出多余矿石
> 前往下一个目标
```

### 8.2 建筑布局

默认武器组合：

```text
第一座：gatling
第二座：railgun
第三座：rocket
```

默认选择基地周围的可建造位置，但必须检查：

- 目标位置在地图范围内。
- 目标位置属于可建造区域。
- 目标位置不是障碍。
- 目标位置没有被其他角色本回合占用。
- 工人与目标相邻。
- 金币不少于 25。

围墙优先围绕基地外沿布置，并保留至少一个通道，避免己方角色被自己建造的围墙困住。

### 8.3 采矿策略

矿石选择分为两类：

```text
石头：满足建墙和应急库存。
铁/铜：根据当前商店价格选择收益更高者。
```

建议库存阈值：

```text
石头安全库存：10
每个待建围墙：额外预留 1
修墙预留：额外预留 2
```

工人到矿区相邻位置时执行 `collect`，否则执行一步移动。
同一回合两个工人不能争抢同一个采集目标或同一个下一步位置。

### 8.4 卖矿策略

卖矿前计算：

```text
可卖数量 = 当前库存 - 安全库存
```

只有可卖数量大于 0 时才卖矿。

优先出售：

1. 当前价格高且不影响任务/建造的矿石。
2. 超过安全库存最多的矿石。
3. 在官方消息预测中可能降价的矿石。

### 8.5 购买策略

购买优先级：

```text
基地升级券
> 核心武器升级券
> WallFixer
> Medicine
> 必需任务用品
> Bomb / DizzyWeapon
> 机器人召唤令
```

购买前检查：

- 当前金币。
- 目标角色背包空间。
- 商店是否提供该物品。
- 是否保留下一次建造或应急防守的金币。

### 8.6 升级策略

默认升级方向：

```text
基地 level1 -> level2
核心武器 level1 -> level2
火箭或电磁炮 level2 -> level3
关键围墙按受损程度升级
```

升级判断：

```text
机器人数量多：优先 Gatling。
高血量机器人多：优先 Railgun。
机器人密集或波次增强：优先 Rocket。
基地血量压力大：优先基地升级。
```

升级券使用失败时不丢弃道具，因此失败后应保留券，等待下一个合法位置或时机。

## 9. 夜间策略

### 9.1 武器控制关系

攻击动作必须由角色提交，武器 ID 放在 `controllerId`：

```json
{
  "角色ID": {
    "action": "attack",
    "controllerId": "武器ID",
    "targetPos": [{"x": 1, "y": 2}]
  }
}
```

不能把武器 ID 作为 `roleCommandMap` 的 key。

默认控制关系：

```text
worker1 -> gatling
worker2 -> railgun
pioneer -> rocket
```

若角色死亡或距离武器超过一格，则选择最近的存活角色补位。

### 9.2 机器人威胁评分

目标选择不只看距离，建议使用：

```text
threat =
    类型权重
  + 基地接近权重
  + 攻击能力权重
  + 低血量收割权重
```

类型初始权重：

```text
bossRobot   1000
largeRobot   500
middleRobot  200
smallRobot   100
```

当机器人距离基地更近时增加威胁分；当机器人已经残血且可以被当前武器击杀时增加收割分。

### 9.3 Gatling 策略

- 优先攻击范围内的多只机器人。
- 多个目标必须尽量落在同一 90 度锥形内。
- 优先处理小型和中型机器人集群。
- 目标数量按武器等级决定。
- 如果多目标无法满足角度约束，退化为单目标攻击。

### 9.4 Railgun 策略

- 优先攻击高血量机器人。
- 优先寻找同一直线路径上的多个机器人。
- 目标不满足直线条件时攻击威胁最高目标。
- 注意武器攻击路径和可穿透规则。

### 9.5 Rocket 策略

- `cooldown > 0` 时不发射。
- 优先选择机器人密度最高的落点。
- 多枚导弹尽量覆盖不同高威胁区域。
- 目标落点应优先靠近基地方向的机器人集群。

### 9.6 防守和道具

夜间每回合首先检查：

```text
基地是否受到直接威胁
关键围墙是否濒临摧毁
是否有高等级机器人突破防线
是否可以使用 Bomb 或 DizzyWeapon
```

紧急情况下：

```text
Bomb：机器人密集且能命中多个目标时使用。
DizzyWeapon：高威胁机器人接近基地时使用。
WallFixer：围墙低血且角色在一格内时使用。
Medicine：角色低血并且仍承担武器控制时使用。
```

## 10. 任务策略

### 10.1 自进化任务

流程：

```text
1. 找到己方且 isValid=true 的任务点。
2. 开拓者移动到任务点周围一格。
3. 执行 acceptTask。
4. 保存 phaseTask 原文。
5. 在任务期间使用 executeCmd 或 prompt。
6. 保存沙盒输出和当前最佳答案。
7. 使用 submitAnswer。
8. 根据 errors 和任务状态判断是否结束。
```

任务期间开拓者不能离开任务点周围一格，否则任务会结束。

### 10.2 沙盒执行策略

`executeCmd` 只在任务期间使用，且单次命令不超过 15 秒。

执行命令应遵循：

- 优先使用本地 Python 和 shell。
- 不依赖外部网络。
- 输出控制在较小范围内。
- 失败后保存错误信息，调整命令再重试。
- 相同问题不要无上限重复执行。

### 10.3 世界新闻和宝藏

每个白天保存：

```text
roundNo
day
officialNews
folkLegends
```

民间传闻解析为候选信息：

```text
候选坐标
候选开启时间
候选任务用品
候选触发条件
```

只有当候选信息达到足够置信度，并且开拓者携带完整物品时，才执行 `summonTreasure`。
献祭物品必须严格匹配，不能多、不能少。

### 10.4 LLM 使用策略

每天最多使用 3 次普通 LLM 调用。

使用原则：

```text
任务答案推理优先
长上下文线索整合其次
普通战斗决策不调用
相同 prompt 使用缓存
额度不足时使用规则策略降级
```

## 11. 动作生成和合法性检查

每个动作输出前必须检查：

```text
角色 ID 属于己方。
角色存活。
action 合法。
targetPos 坐标格式正确。
坐标处于地图范围。
移动目标最多一格。
建造、拆除、采集目标符合相邻要求。
攻击包含有效 controllerId。
controllerId 对应己方武器。
攻击只在黑夜执行。
建造只在白天执行。
任务动作只由开拓者执行。
每个角色最多一条指令。
```

检查失败时只丢弃该角色动作，不能让整个响应变成非法 JSON。

## 12. 冲突处理

建立本回合计划表：

```text
role_id -> command
reserved_positions
reserved_mines
reserved_targets
weapon_controllers
```

冲突处理顺序：

```text
紧急防守动作优先
> 武器攻击
> 任务提交
> 修墙
> 建造
> 采矿
> 普通移动
```

当两个角色计划移动到同一位置时：

1. 保留优先级更高的动作。
2. 另一个角色寻找备选一步路径。
3. 没有备选路径时本回合不发动作。

## 13. 异常和降级策略

### 13.1 输入异常

可选字段缺失时使用空集合或默认值：

```text
缺少 robots：按无机器人处理。
缺少 worldNews：不更新新闻记忆。
缺少 weaponShopList：本回合不购买。
缺少 lastRoundRoleActionResults：按无反馈处理。
```

关键字段缺失或类型错误时：

- 记录日志。
- 返回空 `roleCommandMap`。
- 保持 HTTP 响应为合法 JSON。

### 13.2 指令异常

所有命令在序列化前做校验。
单个角色命令不合法时跳过该命令，不影响其他角色。

### 13.3 服务异常

HTTP 响应始终保持：

```json
{
  "roleCommandMap": {},
  "prompt": "",
  "executeCmd": ""
}
```

日志记录异常堆栈，但不能把堆栈内容直接返回给判题器。

## 14. 实现阶段计划

### 阶段一：协议和状态基础

目标：

- 完整解析 Request。
- 统一构造 Response。
- 支持所有单位和可选字段。
- 修正角色命令与 `controllerId` 的关系。
- 增加动作校验。

验收：

- 使用 `request.txt` 能稳定返回合法 JSON。
- 缺字段请求不会崩溃。
- 每个角色最多一条命令。

### 阶段二：地图和移动

目标：

- 正确处理基地 2×2 占地。
- 统一处理建筑、矿区、中立单位和机器人障碍。
- 处理同回合移动冲突。
- 增加目标预留和备选路径。

验收：

- 不走出地图。
- 不移动到障碍物。
- 两名角色不会主动争抢同一位置。

### 阶段三：白天经济和建筑

目标：

- 石矿、铁矿、铜矿采集。
- 按价格卖矿。
- 武器和围墙建造。
- 商品购买。
- 建筑升级和维修。

验收：

- 金币、库存和背包容量检查正确。
- 资源不足时不生成非法动作。
- 基地周围防线可以逐步完成。

### 阶段四：夜间战斗

目标：

- 武器控制角色分配。
- Gatling、Railgun、Rocket 分别处理。
- 火箭冷却。
- 机器人威胁排序。
- 道具应急使用。

验收：

- 武器攻击命令格式正确。
- 角色能移动到武器附近。
- 高威胁机器人优先被处理。

### 阶段五：任务和记忆

目标：

- 自进化任务流程。
- `executeCmd` 和 `prompt`。
- `submitAnswer`。
- 世界新闻记忆。
- 宝藏线索和献祭物品。

验收：

- 任务期间开拓者不随意离开任务点。
- 任务失败可以降级，不影响战斗响应。
- LLM 调用次数受控。

### 阶段六：模拟、压测和比赛适配

目标：

- 1300 回合模拟。
- 多机器人压力测试。
- 随机地图和随机矿区测试。
- 错误请求和超时测试。
- 日志回放。

## 16. 注释规范

后续实现代码时：

- 对复杂策略前写一段说明目的的注释。
- 对切比雪夫距离、基地占地、武器攻击约束等规则写明来源。
- 对降级逻辑注明为什么返回空动作或跳过单个角色。
- 不为显而易见的赋值和循环添加无意义注释。
- 注释描述“为什么这样做”，而不是重复代码表面含义。

示例：

```python
# 武器攻击命令必须挂在操控角色上，controllerId 才是被操控的武器。
commands[controller.unit_id] = attack_command(
    controller_id=weapon.unit_id,
    targets=targets,
)
```

## 17. 当前决策结论

后续开发遵循以下固定方案：

1. 正式实现目录只有 `Demo/CoreGeek/`。
2. 默认防守阵容为 `gatling + railgun + rocket`。
3. 优先实现稳定协议、地图移动、经济和夜间防守。
4. 任务、宝藏和 LLM 能力在基础战斗稳定后接入。
5. 所有输出动作先校验，再返回给判题器。
6. 所有复杂规则都要有必要注释和测试。

## 18. 实现约束与优先原则

为了避免后续实现过程中策略不断漂移，增加以下固定约束：

### 18.1 单一事实来源

- 正式代码只能放在 `Demo/CoreGeek/`。
- `Demo/CoreGeek.tar.gz`、临时脚本和实验代码不得参与正式运行。
- 任务书规定游戏规则，接口文档规定字段和动作格式，策略文档只规定实现顺序与决策方法。
- 当策略文档与接口文档冲突时，以接口文档为准，并在本文档记录修订点。

### 18.2 先保证响应合法，再追求收益

每回合策略按照以下目标排序：

```text
HTTP 不报错
> JSON 格式正确
> 输出动作合法
> 基地和角色不死亡
> 维持武器防守能力
> 完成经济目标
> 完成任务和宝藏
> 提高资源收益
```

任何不确定的动作都必须降级为确定性动作或空动作，不能因为追求一次高收益而破坏整回合响应。

### 18.3 一个角色只承担一个职责

同一回合内，一个角色只能输出一条动作。策略层需要先生成候选动作，再统一裁决，不能在多个分支中分别写入命令后相互覆盖。

## 19. 回合决策状态机

正式实现建议将策略视为状态机，而不是大量互相覆盖的 `if/else`。

### 19.1 状态定义

```text
INIT              初始化和解析请求
DAY_SAFE          白天安全运营
DAY_EMERGENCY     白天紧急修复或补充防御
NIGHT_PREP        黑夜开始前的武器就位
NIGHT_COMBAT      黑夜战斗
TASK_ACTIVE       执行任务
TREASURE_READY    宝藏条件已满足，等待合法时机
DEGRADED          输入不完整或局部策略失败
```

### 19.2 状态转换

```text
INIT -> DEGRADED       关键字段解析失败
INIT -> DAY_SAFE       当前为白天且基地安全
INIT -> DAY_EMERGENCY  当前为白天且基地/围墙存在高风险
INIT -> NIGHT_PREP     进入黑夜前两个回合
INIT -> NIGHT_COMBAT   当前为黑夜
DAY_SAFE -> DAY_EMERGENCY 关键围墙低血或机器人靠近
DAY_SAFE -> TASK_ACTIVE    当前任务具有高置信度且不影响防守
DAY_SAFE -> TREASURE_READY 宝藏条件满足
NIGHT_PREP -> NIGHT_COMBAT 黑夜正式开始
任意状态 -> DEGRADED      当前动作无法通过校验
```

状态只影响决策优先级，不改变接口输出格式。服务重启后允许从 `INIT` 重新开始。

### 19.3 状态退出条件

- `DAY_EMERGENCY`：基地和关键围墙恢复到安全阈值，或已没有可执行的修复动作。
- `TASK_ACTIVE`：任务完成、任务失败、任务反馈超时或防守风险升高。
- `TREASURE_READY`：成功召唤、条件失效或当天不再满足时机要求。
- `NIGHT_COMBAT`：进入下一白天。

## 20. 统一评分与决策裁决

所有候选动作先计算评分，再按角色和资源约束筛选。评分不要求绝对准确，但必须稳定、可解释、方便测试。

### 20.1 动作评分

建议使用以下形式：

```text
score =
    survival_value
  + objective_value
  + resource_value
  - distance_cost
  - risk_cost
  - conflict_cost
```

推荐初始权重：

```text
基地保命       +1000
阻止机器人突破  +800
控制未分配武器  +600
修复关键围墙    +500
任务提交        +400
完成必要建造    +300
采集稀缺资源    +150
普通移动        +10
无法确认结果    -300
进入敌方高风险格 -800
```

实现时不要直接比较不同类型的原始数值，例如不要把金币数量直接与基地血量相加；应先转成同一评分尺度。

### 20.2 候选动作裁决顺序

每个角色最多保留一项候选动作，裁决顺序为：

1. 会立即避免基地受损的动作。
2. 会阻止机器人进入基地攻击范围的动作。
3. 会恢复关键武器或围墙能力的动作。
4. 会完成已开始的任务或提交答案的动作。
5. 会产生资源收益的动作。
6. 普通移动和等待。

如果两个动作分数相差不超过 10，优先选择风险更小、路径更短、依赖字段更少的动作。

## 21. 资源预算与安全线

策略不能把所有资源都投入当前收益动作，必须保留应急库存。

### 21.1 金币分层

金币按用途分成三层：

```text
生存金：修墙、治疗、紧急防守，任何时候不得主动花空。
建设金：下一座武器或必要围墙的预算。
运营金：升级、购买、任务和其他可延后消费。
```

默认规则：

```text
可支配金币 = 当前金币 - 生存金 - 下一项建设预算
```

只有可支配金币大于 0 时，才执行非必要购买。

### 21.2 资源库存

维护以下最低库存：

```text
石头：满足当前围墙计划 + 2 个应急围墙
治疗品：至少 1 个，若武器控制角色低血则提高到 2 个
攻击道具：至少 1 个，除非当前没有可用角色或武器
```

当库存低于安全线时，卖矿和非必要升级自动暂停。

### 21.3 资源获取目标

每名工人只保留一个当前目标：

```text
目标矿点 -> 目标相邻格 -> 采集 -> 背包满时返回基地/卖矿点
```

目标完成或失效后才重新选择，避免每回合在多个矿点之间抖动。

## 22. 地图移动与路径策略细化

### 22.1 目标点转换

角色通常不能直接站在建筑、矿点或任务点上执行动作，因此所有目标都要转换为“可执行相邻格”：

```text
原始目标点
-> 生成周围候选格
-> 删除越界、障碍、己方占用和敌方威胁格
-> 按距离和风险排序
-> 选择第一个可到达格
```

任务点、武器、基地和矿点都使用同一套目标点转换逻辑。

### 22.2 路径选择规则

路径排序建议为：

```text
路径长度
> 是否经过机器人相邻格
> 是否经过即将建造的区域
> 是否与其他角色目标冲突
```

如果最短路径经过高风险格，允许增加最多 2 步绕行；超过该上限则返回低风险等待或切换备用目标。

### 22.3 路径失败处理

同一目标连续两回合无法到达时：

1. 重新计算障碍，排除已经失效的占用信息。
2. 尝试备用相邻格。
3. 仍然失败则将目标标记为暂不可用。
4. 角色切换到同优先级的备用目标。

不得每回合无限重复相同路径，避免角色原地抖动。

## 23. 夜间防守细化

### 23.1 防线分区

将基地周围划分为三层：

```text
内圈：基地占地和紧邻格，禁止非必要角色离开防守。
中圈：围墙、武器和主要射击位置。
外圈：机器人进入后的预警区和拦截区。
```

当机器人进入内圈时，所有白天目标暂停，角色只保留攻击、道具、治疗或修墙动作。

### 23.2 威胁等级

```text
P0：机器人已经进入基地攻击范围
P1：机器人进入中圈，下一回合可能突破
P2：机器人进入外圈，暂时可由武器覆盖
P3：远离基地且没有有效路径
```

处置原则：

```text
P0：所有可用武器集中处理，必要时使用攻击道具
P1：分配至少一座武器持续攻击，并修复对应防线
P2：按武器类型和范围分配，不提前消耗稀有道具
P3：保持武器就位，除非没有其他目标
```

### 23.3 武器失效降级

- 没有控制角色时，优先安排距离最近且不会离开内圈的角色。
- 武器冷却中时，控制角色执行就位、治疗或等待，不重复发射。
- 目标超出范围时，选择范围内次高威胁目标。
- 无有效目标时，不输出伪攻击动作，改为防守位置移动或空动作。

## 24. 任务、新闻与宝藏的风险控制

### 24.1 任务准入条件

只有同时满足以下条件才开始任务：

```text
开拓者存活
任务点可达
至少一名角色可承担基础防守
基地风险不高于 P2
预计任务收益高于离开岗位的机会成本
```

任务一旦开始，除 P0/P1 防守事件外，不随意切换回普通采矿。

### 24.2 任务失败重试

任务失败后记录：

```text
任务标识
失败原因
已经消耗的回合
已经使用的 LLM 次数
最后一次有效答案
```

相同失败原因最多自动重试一次。再次失败时转入规则策略，避免浪费每日调用额度。

### 24.3 新闻置信度

新闻线索分为：

```text
高：官方消息明确给出坐标、时间或物品
中：多条民间传闻指向同一目标
低：单条模糊传闻，缺少可验证条件
```

只有高置信度线索可以直接触发宝藏行动；中置信度线索需要先验证；低置信度线索只保存，不消耗关键资源。

## 25. 日志、可观测性与回放

正式实现必须支持足够的日志，但不能把调试信息写入接口响应。

每回合至少记录：

```text
roundNo、day、phase
基地血量、围墙最低血量、机器人数量
角色位置、角色目标、候选动作
最终动作、动作裁决原因
金币和关键库存
解析失败、校验失败和降级原因
```

日志要求：

- 默认使用简洁单行格式，便于按回合搜索。
- 不记录完整任务答案、敏感凭据或无关的大段上下文。
- 关键错误带有字段名和动作名，便于定位接口问题。
- 能够根据日志复盘“为什么选择这个动作”。

## 26. 验收指标

后续每个阶段都必须通过明确指标，而不是只确认程序“能运行”。

### 26.1 协议指标

```text
100% 测试请求返回合法 JSON
100% 缺少可选字段的请求不崩溃
非法动作不会进入最终响应
每个角色最多一条动作
```

### 26.2 策略指标

```text
130 回合模拟中昼夜切换正确
角色不会连续两个回合选择同一不可达目标
两角色不会长期争抢同一位置
夜间每座可用武器都有控制或明确的待命原因
金币不足、背包已满、武器冷却时不会重复执行失败动作
```

### 26.3 稳定性指标

```text
异常输入能够降级到空动作响应
单个角色动作失败不影响其他角色
任务或 LLM 失败不影响夜间防守
服务连续处理长回合输入后内存和日志规模可控
```

## 27. 后续实现顺序

在开始修改代码时，严格按以下顺序推进：

1. 先补协议解析和响应封装。
2. 再补阶段判断、状态快照和动作校验。
3. 再补地图目标点转换、路径和冲突处理。
4. 再补白天资源、建造、购买和升级。

每完成一个阶段，先运行对应测试和样例请求，再进入下一阶段。不得在协议尚未稳定时同时引入复杂任务逻辑。
