# 功能实现说明

> 最后更新：2026-09-17
>
> 本文把《任务书》、 《接口文档》、`request.txt`、`response.txt` 与当前源码逐项对照。文中“已实现”只表示源码中能找到对应逻辑，不表示已经在公司服务器或真实对局中验证成功。

## 1. 先看结论

当前程序可以理解成一个“会自动采矿、造防御设施、夜间开炮”的基础机器人：

- 能启动一个 HTTP 服务；
- 能接收判题器发来的回合 JSON；
- 能识别白天和黑夜；
- 白天让工人采集矿石、建造武器和围墙，并按预算购买升级券；
- 夜晚让角色靠近武器，并操控武器攻击机器人；
- 能在地图上绕开部分障碍寻找下一步；
- 能返回接口要求的 `roleCommandMap` 外壳。

但任务书要求的完整玩法远远不止这些。当前已经有基础卖矿、购买维护用品和升级券、使用维护用品和升级券、领取任务入口；仍没有完整实现拆墙、回答任务、召唤宝藏、使用攻击道具策略、丢弃物品、LLM 调用、世界新闻分析、攻击敌方玩家和根据对手变化调整策略。

## 2. 当前代码的工作流程

```text
判题器 POST JSON
      ↓
main3.py 启动端口
      ↓
server.py 读取 JSON
      ↓
protocol.py 把部分状态变成 Python 对象
      ↓
brain.py 按白天/黑夜生成动作
      ↓
server.py 返回 {"roleCommandMap": {...}}
```

主要文件：

- [main3.py](../Demo/CoreGeek/main3.py)：程序入口，读取端口并启动服务。
- [server.py](../Demo/CoreGeek/src/agent/server.py)：HTTP 接收、调用决策、返回 JSON。
- [protocol.py](../Demo/CoreGeek/src/agent/protocol.py)：坐标、角色、机器人和动作格式。
- [brain.py](../Demo/CoreGeek/src/agent/brain.py)：白天和黑夜的决策规则。
- [grid.py](../Demo/CoreGeek/src/agent/grid.py)：寻找移动路径的下一步。

## 3. 已实现功能详表

| 功能 | 当前实现 | 代码位置 | 现状判断 |
|---|---|---|---|
| HTTP 服务 | 监听 `0.0.0.0:<port>`，接收 POST | `server.py`、`main3.py` | 有基础实现，服务器待验证 |
| JSON 解析 | 读取请求体并解析 JSON | `server.py` | 有实现，但错误会被吞掉 |
| 回合判断 | 70 回合白天、60 回合黑夜，130 回合一个游戏日 | `protocol.py` | 有实现，需用样例确认回合起点 |
| 地图读取 | 读取宽、高和 zones | `protocol.py:Turn.load` | 有实现，当前已支持三种矿和中立区域基础识别 |
| 角色读取 | 读取我方角色的 ID、位置、类型、血量、等级、背包等 | `protocol.py:Unit.load` | 有实现 |
| 机器人读取 | 读取机器人 ID、位置、血量、异常状态和攻击阵营 | `protocol.py:Robot.load` | 已实现字段读取，策略仍需使用这些信息 |
| 切比雪夫距离 | 使用 `max(abs(dx), abs(dy))` | `protocol.py:distance` | 与任务书一致 |
| 地图寻路 | 通过优先队列找下一步，避开部分阻挡物 | `grid.py:next_step` | 有实现，需检查边界和拥挤碰撞 |
| 白天采集矿石 | 工人寻找石、铁、铜矿，靠近后执行 `collect` | `brain.py:_mine`、`_trade_or_mine` | 已支持基础采集，资源优先级仍需优化 |
| 小贩交易 | 工人有矿石时前往小贩，相邻后批量卖出 | `brain.py:_trade_or_mine` | 已有基础闭环；价格策略仍待实现 |
| 治疗和修墙 | 受伤角色会前往商店购买/使用 `Medicine`；工人会购买/使用 `WallFixer` 修复受损围墙 | `brain.py:_maintain` | 已实现基础维护；服务器对局待验证 |
| 建筑升级 | 按武器、基地、围墙顺序选择未满级建筑；按商店价格购买对应升级券并在建筑旁使用 | `brain.py:_upgrade`、`_upgrade_plan` | 已实现基础闭环；服务器对局待验证 |
| 基础攻击道具 | 基地附近出现至少两个机器人时，优先使用背包中的 `Bomb`，否则使用 `DizzyWeapon` | `brain.py:_use_defense_item` | 已实现基础使用条件；购买时机和服务器效果待验证 |
| 白天建造武器 | 金币不少于25时，按固定顺序建造加特林、电磁炮、火箭 | `brain.py:_worker_day` | 有实现，但不考虑真实资源规划和升级 |
| 白天建造围墙 | 有石头时按基地周边固定位置建墙 | `brain.py:_wall_order` | 有实现，位置和策略较死 |
| 夜间操控武器 | 让可控制角色靠近武器，操控武器攻击机器人 | `brain.py:_night` | 有实现，但目标选择和武器规则不完整 |
| 攻击目标选择 | 优先选择正在攻击我方阵营且位于射程内的机器人 | `brain.py:_attack_targets` | 有基础实现，仍需按血量和机器人类型细化 |
| 动作格式构造 | 已构造动作全集的参数对象 | `protocol.py` | 决策策略目前只主动使用部分动作 |
| 异常兜底 | 决策失败时返回空 `roleCommandMap` | `server.py` | 有兜底，但可能隐藏错误并造成比赛失分 |

## 5. 当前代码尚未充分使用的接口数据

`Turn.load` 已经保存下列主要接口资料，但部分资料还没有真正参与决策：

- `teamOur.type`、`teamId`、`totalScore`；
- `playerTasks`；
- `teamEnemy`；
- `Robot.abnormalState`、`targetTeam`；
- `phaseTask`、`lastRoundRoleActionResults`；
- `lastSummonTreasureResult`、`llmResp`、`worldNews`、`lastCmdResult`；
- `vendorShopList`、`weaponShopList`；
- `errors`。

程序目前已经使用队伍类型、任务点、敌方单位、机器人目标、上一回合动作结果和商店价格；`errors`、`worldNews`、`llmResp`、`lastCmdResult` 和宝藏结果仍只读取不决策。

## 6. 最需要改进的问题

### 6.1 先修“规则正确性”

优先保证每一条动作都合法，否则可能累计异常。建议先做：

1. 统一请求对象和响应对象，完整保存接口字段。
2. 给每种动作建立参数校验：角色类型、昼夜、距离、目标位置、背包、金币和冷却。
3. 使用 `lastRoundRoleActionResults` 发现动作失败后，下一回合换策略，不要重复发同一条错误指令。
4. 在发送前检查每个角色每回合最多一条指令。
5. 不要只在异常时返回空动作；至少记录清楚是哪一步解析或决策失败。

当前还有一个具体风险：白天多个工人可能在同一回合都看到同一个金币余额，并分别决定建造武器，但代码没有在决策中扣除“本回合已经计划花掉的钱”。金币不足时，后面的建造指令可能变成非法指令。资源预算和同回合动作冲突检查应优先补上。

### 6.2 再补齐“生存能力”

任务书的核心目标是坚持10天或击败对手。当前策略只会固定采矿、建造和打机器人，建议补充：

- 根据机器人 `targetTeam`、距离、血量和类型决定先打谁；
- 处理武器冷却和多目标攻击；
- 明确检查武器建造位置是否属于规则允许的武器建造区域，而不是只检查 `land`；
- 保护基地入口，动态修墙、拆墙和补墙；
- 角色死亡后的复活和重新分工；
- 发现敌方单位或敌方进攻时改变防守位置；
- 用金币和矿物做资源预算，而不是只判断“金币是否不少于25”。

### 6.3 最后补齐“得分能力”

任务书明确包含做任务、升级、防守积分和宝藏等内容。建筑升级基础闭环已经加入，后续还要补：

- 根据动态价格优化卖矿；
- 武器商店购买攻击道具和召唤令；
- 开拓者领取任务、读取任务文本、提交答案；
- 使用 LLM 时控制每日3次额度，并保存上一回合结果；
- 根据官方消息、民间传闻和任务类型选择策略；
- 召唤宝藏并根据结果码处理重试或换祭品。

## 8. 当前完成度的正确说法

可以说：“程序已经实现 HTTP 基础服务，以及采集、交易、购买维护用品和升级券、建筑升级、建造、寻路和夜间基础攻击逻辑。”

不能说：“程序已经完整实现 v1.0”或“策略已经验证有效”。因为任务书规定的动作尚未全部实现，并且还没有公司服务器真实对局证据。
