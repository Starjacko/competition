## 1. 项目用途

这是一个公司内部编程大赛的参赛程序。比赛系统每回合通过 HTTP 把地图和队伍状态发给本程序，本程序根据当前状态生成角色动作，再把动作返回给判题器。

比赛最终需要在公司内部服务器上运行，并和另一名员工编写的参赛程序进行真实对局。本地只能做局部检查，不能证明完整策略有效。

## 3. 整体架构

项目是一个单进程、无数据库的 HTTP 决策服务：

```text
公司判题器
    │ 每回合 POST JSON
    ▼
main3.py —— 启动程序、读取端口、设置 src 路径
    ▼
server.py —— 接收请求、解析 JSON、返回 roleCommandMap
    ▼
brain.py —— 根据白天/黑夜选择策略并生成动作
    ├── protocol.py —— 把 JSON 状态转换成 Turn、Unit、Robot 等对象
    └── grid.py —— 避开障碍物寻找下一步移动位置
```

没有发现传统的数据库层、前端层或独立后端框架。`server.py` 同时承担 HTTP 接入和异常兜底，`brain.py` 是主要决策层。

## 4. 启动流程

入口文件是 [main3.py](../Demo/CoreGeek/main3.py)。它要求传入一个端口：

```bash
python main3.py <port>
```

启动时会：

1. 检查命令行是否只传入一个端口。
2. 把当前目录切换到 `Demo/CoreGeek`。
3. 把 `src` 加入 Python 模块搜索路径。
4. 导入 [server.py](../Demo/CoreGeek/src/agent/server.py) 中的 `serve`。
5. 在 `0.0.0.0:<port>` 上启动多线程 HTTP 服务。

比赛接口文档中的示例启动方式是 `bash run.sh port`，但当前仓库没有发现 `run.sh`。因此，公司服务器上的最终启动命令仍需确认。

## 5. 每回合数据流

### 5.1 接收请求

[Handler.do_POST](../Demo/CoreGeek/src/agent/server.py) 读取 HTTP 请求体，并使用 JSON 解析为 Python 字典。

### 5.2 解析状态

[Turn.load](../Demo/CoreGeek/src/agent/protocol.py) 从请求中提取：

- 当前回合数；
- 地图宽度、高度和中立区域；
- 我方金币、角色、任务和阵营；
- 敌方可见角色与场上的机器人；
- 上回合动作结果、商店清单、错误、新闻和任务相关结果。

它还根据回合数判断当前是白天还是黑夜。

### 5.3 生成决策

[decide](../Demo/CoreGeek/src/agent/brain.py) 根据昼夜进入不同策略：

- 白天调用 `_day`；
- 黑夜调用 `_night`。

### 5.4 返回响应

决策结果会被包装成：

```json
{
  "roleCommandMap": {
    "角色ID": {
      "action": "动作名称"
    }
  }
}
```

如果解析或决策发生异常，服务会记录异常，并返回空的 `roleCommandMap`。这能避免进程直接崩溃，但是否会被判题器计为异常，需要服务器实测确认。

## 7. 当前策略范围

从源码可以确认当前程序主要实现了：

- 白天/黑夜判断；
- 工人采集石、铁、铜矿并前往小贩卖矿；
- 工人建造最多三座预设武器；
- 工人围绕基地建造围墙；
- 购买和使用药品、修墙包和建筑升级券；
- 开拓者前往有效任务点并领取任务；
- 夜晚让角色操控武器攻击机器人；
- 基于地图障碍物的移动寻路。

从当前源码没有确认已经实现的能力包括：

- 更完整的建筑升级策略（基础升级券流程已实现）；
- 根据动态价格优化卖矿；
- 任务答案提交；
- LLM 调用；
- 世界新闻分析；
- 民间传闻和宝藏推理；
- 召唤机器人、使用道具和主动攻击敌方玩家。

这些内容是否属于当前版本目标，需要先记录为需求并由项目负责人确认。
